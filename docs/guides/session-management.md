# Управление сессией

Жизненный цикл сессии, два лимита контекста, деградация качества
и обработка ошибок перехода. Читать после [Использования](usage.md).

## Что такое сессия

Сессия = API-ключ + активный чат в DeepSeek + `chat_state.json` +
(опционально) `rag_data/<key>.linear.json`. Живёт, пока сервер не
завершится или клиент не вызовет `/v1/chat/new {restore: false}`.

Изоляция сессий:
- **API-ключ** — идентификатор сессии. Разные ключи → разные `chat_state`
  и разные RAG-индексы.
- **`chat_state.json`** — один файл на процесс. При смене ключа через
  `/v1/register` файл перезаписывается.
- **`rag_data/<key>.linear.json`** — один файл на ключ. Не пересекаются.

## Жизненный цикл

```
register
  │
  ├─ первый запрос ──────────────────────────────► ответ
  │                                                   │
  │                                          totalChars растёт
  │                                                   │
  │                                          ┌────────┴────────┐
  │                                      70% │                 │ 90%
  │                                          ▼                 ▼
  │                                    snapshot          transition
  │                                    создан            в новый чат
  │                                          │                 │
  │                                          └────────┬────────┘
  │                                                   │
  │                                          новый чат активен
  │                                                   │
  │                              ┌────────────────────┴──────────────┐
  │                              │                                   │
  │                         ENABLE_RAG                        ENABLE_SNAPSHOT
  │                              │                                   │
  │                        ragSearchActive                  snapshot.txt
  │                        = true                           загружен
  │                              │                                   │
  │                              └────────────┬──────────────────────┘
  │                                           │
  │                                     продолжаем работу
  │                                           │
  │                                   70% → 90% → transition
  │                                           │
  │                                         ...цикл...
  │
  └─ 409 context_exhausted ──► /v1/chat/new ──► повторить
```

Каждый переход — **новый чат**, не продолжение старого.

## Параметры модели

На сентябрь 2026 Web-версия DeepSeek работает на модели
**DeepSeek-V4.1-Flash** (`deepseek-flash` в API):

| Параметр | Значение |
|---|---|
| Контекстное окно | 1 048 576 токенов (≈1M) |
| Максимальный вывод | 384 000 токенов |
| Ввод | Текст + изображения |
| Параметров (всего / активных) | 552B / 8B (вход), 16B (выход) |
| Режимы | Thinking / Non-thinking |

V4.1 Flash заменил V4 Flash и V4 Flash Vision Exp (июнь–сентябрь 2026).
Старые API-имена (`deepseek-v4-flash`, `deepseek-v4-flash-vision-exp`)
временно роутятся на новую модель.

## Два лимита контекста

### Расчётный лимит

Формула:

```
chars_limit = 1 000 000 × language_coefficient
```

`language_coefficient` вычисляется из языкового состава первых
500–5000 символов пользовательских сообщений:

| Язык | Коэффициент | Символов на 1M токенов | Обоснование |
|---|---|---|---|
| Латиница | 3.0 | ≈ 3 333 333 | 0.3 токена на символ; запас ~10% на служебные токены |
| Кириллица | 2.4 | ≈ 2 400 000 | 0.42 токена на символ; калибровка на реальном UI |
| CJK | 1.0 | ≈ 1 666 667 | 0.6 токена на символ; консервативная оценка из-за латиницы в CJK-тексте |

Чистых языков в сессиях почти не бывает. Коэффициент смешивается
пропорционально долям символов:

```
coefficient = w_latin × 3.0 + w_cyrillic × 2.4 + w_cjk × 1.0 + w_other × 2.0
```

Появляется в каждом `context_status`. Клиент может отслеживать
приближение заранее.

### Реальный лимит

DeepSeek возвращает баннер «Length limit reached. DeepSeek can only
read the first N%...». Это **ground truth** — сколько сервер
фактически прочитал из отправленного. Появляется только в момент
переполнения, заранее невидим.

В `context_status` отражается как:

```json
"deepseek_length_limit": {
  "detected": true,
  "readable_percent": 75
}
```

При переполнении клиент получает HTTP 409, в теле которого:

```json
"error": {
  "type": "context_exhausted",
  "chars_used": 2345678,
  "chars_limit": 2400000,
  "deepseek_readable_percent": 75,
  "rag_enabled": true,
  "recovery": "Call POST /v1/chat/new..."
}
```

### Почему они расходятся

Наш `language_coefficient` — эвристика. DeepSeek считает **токены**,
мы считаем **символы**. Соотношение зависит от:

- языка (латиница / кириллица / CJK / смесь),
- типа текста (код / проза / формулы),
- длины сессии (служебные токены накапливаются).

Точность ±20% — норма. Расхождение не bug, а следствие того, что
мы работаем поверх UI, а не через API.

### Как калибровать

Если 409 приходит с `readable_percent = 75`, а `chars_used / chars_limit = 0.95`
— наш лимит **завышен** на ~25%. Уменьшите `DEEPSEEK_MAX_CONTEXT_CHARS`
или проверьте `language_coefficient` в `context_status`.

Если 409 приходит с `percent_used = 60` — наш лимит **занижен**.
Увеличьте `DEEPSEEK_MAX_CONTEXT_CHARS`.

Для большинства сценариев калибровка не требуется: система переходит
в новый чат **раньше**, чем DeepSeek вернёт баннер. Баннер — аварийный
путь, а не штатный.

## Деградация качества

Ключевое, что должен понимать клиент API.

### Что происходит технически

При достижении 90% (или при баннере) `DeepSeekClient.handleOverflow()`
открывает новый чат. Старый чат **остаётся в сайдбаре** — к нему можно
вернуться через `/v1/chat/new {restore: true}`, но текущая сессия
работает в новом.

Новый чат — это **пустой контекст**. Модель не знает ничего о предыдущем
диалоге. Система передаёт ей только то, что может:

### Что передаётся

| Механизм | Что передаётся | Размер |
|---|---|---|
| **Snapshot** | Сжатая версия диалога через DeepThink | ~10% от лимита |
| **RAG** | Top-5 фрагментов, семантически близких к **текущему запросу** | ≤ 1200 символов на фрагмент |
| **Оба** | Снапшот сразу + RAG по запросу | Сумма |

### Что теряется

| Механизм | Что теряется |
|---|---|
| Snapshot | Все детали, не попавшие в summary. Дословные формулировки. Конкретные примеры, если они не были ключевыми. |
| RAG | Фрагменты, не относящиеся к текущему запросу. Модель не «помнит» их — она видит только близкие. |
| Оба | Снапшот даёт структуру, RAG — детали, но они **не связаны**. Модель может «забыть» контекст, в котором фрагмент был релевантен. |
| Ни один | Всё, кроме последнего сообщения. |

### Почему качество падает даже при обоих механизмах

Даже когда модель получает и снапшот, и RAG-фрагменты, она относится
к ним как к **документам**, а не как к своей памяти. Это меняет:

- **Тон.** Ответы становятся формальнее, менее уверенными.
- **Ссылки на историю.** «Как мы обсуждали ранее» → «согласно
  приложенному документу».
- **Детализацию.** Модель не додумывает контекст, которого нет
  в документе. Если в снапшоте не хватает детали — ответ будет
  общим.
- **Логику.** Если в старой сессии было неявное соглашение
  (например, «все суммы в рублях»), оно потеряется, если не попало
  в снапшот или не всплыло в RAG.

### Что делать клиенту

**1. Держать критичное в `system`-сообщении.**

`system`-сообщение пересылается с каждым запросом и не теряется при
переходе. Всё, что должно «пережить» переход — имена, цели, ограничения,
формат ответа — в `system`, а не в истории `messages`.

**2. Планировать переход заранее.**

При `warning = context_above_70` сохранять локально всё, что важно.
При `warning = context_near_limit` — быть готовым к следующему
запросу в новом чате.

**3. Переозвучивать после перехода.**

После 409 и вызова `/v1/chat/new` — отправить короткое сообщение
с ключевыми фактами. Модель «увидит» их в новом контексте.

**4. Не полагаться на дословное восстановление.**

Если ответ должен содержать точную цитату из старой сессии —
передайте цитату в новом сообщении. Не ждите, что снапшот или RAG
восстановят её дословно.

**5. Настроить `ENABLE_SNAPSHOT` и `ENABLE_RAG` под сценарий.**

- Короткие сессии → оба выключены.
- Длинные диалоги с сохранением структуры → `ENABLE_SNAPSHOT=true`.
- Длинные диалоги с частыми тематическими возвратами → `ENABLE_RAG=true`.
- Максимальное качество → оба включены.

## Обработка ошибок

### HTTP 409 context_exhausted

**Сигнал:** DeepSeek достиг лимита. Следующий запрос в том же чате
не имеет смысла.

**Тело:**
```json
{
  "error": {
    "type": "context_exhausted",
    "chars_used": 2345678,
    "chars_limit": 2400000,
    "deepseek_readable_percent": 75,
    "partial_response": "...",
    "rag_enabled": true,
    "recovery": "Call POST /v1/chat/new..."
  }
}
```

**Что делать:**
1. Прочитать `partial_response` — там может быть начало ответа.
2. Прочитать `rag_enabled` — от этого зависит, сохранится ли память.
3. Вызвать `POST /v1/chat/new {restore: false}` — сброс.
4. Повторить исходный запрос в новом чате.

**Чего не делать:**
- Не retry-ить тот же запрос в том же чате — снова получите 409.
- Не вызывать `restore: true` — вернётесь в переполненный чат.

### HTTP 503 server_busy

**Сигнал:** DeepSeek backend отказывает. Возвращается плашка
«Server busy, please try again later».

**Тело:**
```json
{
  "error": {
    "type": "server_busy",
    "message": "DeepSeek backend is not responding. Server shutting down."
  }
}
```

**Что делать:**
1. Сервер **сам завершится** через 500 мс — это by design.
2. Сохранить состояние клиента локально.
3. Дождаться перезапуска сервера (внешний супервизор).
4. Не retry-ить сразу — DeepSeek отказывает часами.

**Чего не делать:**
- Не пытаться отправить тот же запрос повторно — сервер уже упал.
- Не рассчитывать на автоматический перезапуск — если супервизор
  не настроен, сервер останется выключенным.

### HTTP 401 invalid_key

**Сигнал:** ключ не совпадает с сохранённым в `.api-key`.

**Что делать:**
1. Проверить, что используется правильный ключ.
2. Если ключ утерян — вызвать `POST /v1/register` для нового.

### HTTP 504 timeout

**Сигнал:** сервер не дождался ответа DeepSeek за 20 минут.

**Что делать:**
1. Retry с экспоненциальным backoff (1с, 2с, 4с, максимум 3 попытки).
2. Если все попытки неудачны — вероятно, DeepSeek завис. Дождаться
   восстановления.

### HTTP 400 validation_error

**Сигнал:** запрос не прошёл валидацию.

**Возможные причины:**
- `messages` не массив или пустой.
- Роль не из `{user, assistant, system}`.
- `tools` содержит не-`function` элемент.
- Невалидный JSON в `data` (multipart).

**Что делать:** исправить запрос и повторить. Это не транзиентная
ошибка.

## Рекомендуемая архитектура клиента

### Диаграмма состояний

```
         ┌──────────┐
         │  IDLE    │
         └────┬─────┘
              │ отправить запрос
              ▼
     ┌─────────────────┐
     │  WAITING        │
     │  (HTTP request) │
     └────┬────────────┘
          │
     ┌────┴────┬──────────┬─────────┬────────┐
     │         │          │         │        │
    200       400        401       409      503/504
     │         │          │         │        │
     ▼         ▼          ▼         ▼        ▼
 ┌────────┐ ┌──────┐ ┌────────┐ ┌───────┐ ┌──────────┐
 │SUCCESS │ │ FAIL │ │REGISTER│ │NEW    │ │BACKOFF / │
 │        │ │      │ │        │ │CHAT   │ │WAIT      │
 └───┬────┘ └──────┘ └────┬───┘ └───┬───┘ └────┬─────┘
     │                    │         │          │
     │ проверить          │         │          │
     │ context_status     │         │          │
     ▼                    ▼         ▼          ▼
 ┌────────┐             IDLE     RETRY       IDLE
 │warning?│
 └───┬────┘
     │
  ┌──┴──┐
  │     │
 нет   да
  │     │
  ▼     ▼
 IDLE  ЛОГИРОВАТЬ
       (готовиться)
```

### Ключевые правила

1. **Всегда проверять `context_status`** в успешном ответе, даже если
   код 200. Это единственный ранний сигнал.
2. **Логировать каждое изменение `warning`.** Переход
   `null → context_above_70 → context_near_limit` — это прогрессия,
   которую нужно видеть.
3. **При `context_near_limit`** — готовиться к переходу. Сохранить
   состояние, если это stateful-клиент.
4. **При 409** — читать `recovery`, вызывать `/v1/chat/new`, повторять.
5. **При 503** — ждать перезапуска сервера. Не retry-ить сразу.
6. **При 401** — перерегистрироваться через `/v1/register`.
7. **При 504** — retry с экспоненциальным backoff, максимум 3 попытки.
8. **Критичные факты — в `system`**, не в `messages`. Иначе теряются
   при переходе.
9. **Не использовать OpenAI SDK для продакшена.** SDK скрывает
   `context_status` и точные коды ошибок. Используйте `fetch` /
   `requests` напрямую.

### Минимальный health-check клиента

```python
def check_session_health(api_key):
    r = requests.get(
        f"{BASE_URL}/v1/context/status",
        headers={"Authorization": f"Bearer {api_key}"},
    )
    if r.status_code == 503:
        return "client_not_ready"
    if r.status_code == 401:
        return "invalid_key"

    status = r.json()
    pct = status["percent"]

    if pct >= 90:
        return "transition_imminent"
    if pct >= 70:
        return "watch"
    return "ok"
```
