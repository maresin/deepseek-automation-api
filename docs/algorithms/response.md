# Отправка сообщения и ожидание ответа

Алгоритмы B1–B7 описывают путь одного запроса от построения промпта
до получения ответа (или ошибки), и поведение системы при особых
состояниях интерфейса DeepSeek.

---

## B1. Построение промпта из messages {#b1}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Преобразовать массив messages в формате OpenAI в единый текстовый
промпт, который будет введён в поле ввода DeepSeek.

### Входные данные

- `messages: Array<{role, content}>` — массив сообщений с ролями
  `system` / `user` / `assistant`.
- `tools: Array<object> | undefined` — массив инструментов в формате
  OpenAI tool calling.

### Выходные данные

Строка — итоговый промпт для отправки в UI.

### Псевдокод

```
1. Определить, нужны ли префиксы ролей:
      needPrefixes = (есть хотя бы один system) OR (messages.length > 1).
2. Если messages содержит ровно одно user-сообщение без префиксов:
      вернуть content как есть.
3. Иначе — склеить все сообщения, добавляя префикс роли:
      "System: <content>\n"
      "User: <content>\n"
      "Assistant: <content>\n"
4. Если переданы tools — добавить блок с их JSON-описанием и
   инструкцией отвечать JSON при вызове инструмента.
5. Вернуть (toolsBlock + conversationText).
```

### Граничные случаи

- **Одно user-сообщение, без system.** Префикс не добавляется —
  сохраняется обратная совместимость с простыми запросами,
  где пользователь ожидает «чистый» вопрос без обвязки.
- **Только system-сообщение.** Префиксы добавляются, потому что
  есть `hasSystem`. Итог: одна строка `System: ...`.
- **Несколько system.** Все получают префикс `System:`.
- **Инструменты без messages.** Не бывает в текущем API, но
  buildPrompt корректно вернёт только toolsBlock.

### Почему именно так

**Почему префиксы ролей в тексте, а не через UI-функцию.**
У DeepSeek Web нет разделения на system/user/assistant в UI.
Всё вводится как одно сообщение. Единственный способ передать роли —
явные текстовые префиксы, которые модель обучена распознавать.

**Почему `needPrefixes` пропускает одно user-сообщение.**
Ранние версии клиентов (и примеры в `examples/`) обращаются
к API с одним простым сообщением. Если добавить `User:` ко всем
таким запросам, ответы модели начнут отклоняться от обычного чата.
Сохранение «как есть» без префикса устраняет регрессию.

**Почему toolsBlock идёт перед messages.** Модель читает промпт
сверху вниз. Инструкция о формате ответа должна попасть в контекст
до самого вопроса, чтобы при первом же ответе модель уже знала
правила.

### Реализация

- `server-modules/utils.js` → `buildPrompt()`

## B2. Ожидание завершения ответа (Stop / Continue) {#b2}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 3 (добавлена прокрутка вниз перед проверкой футера)

### Назначение

Дождаться полного ответа ассистента, обрабатывая состояния интерфейса
DeepSeek: генерацию, паузу с кнопкой Continue, длинные ответы вне viewport.

### Входные данные

- `lastKey: number` — максимальный `data-virtual-list-item-key` перед
  отправкой сообщения. Позволяет вычислить ключ будущего ассистентского
  сообщения.
- `timeoutMs: number` — общий бюджет времени (по умолчанию 20 минут).

### Выходные данные

Полный текст ответа ассистента, либо выброшенное исключение
`ContextExhaustedError` / `Error`.

### Псевдокод

```
1. assistantKey := lastKey + 2
   deadline     := now + timeoutMs
2. Для iter = 0 .. MAX_CONTINUE (20):
     a. step := waitForChunkComplete(deadline)   (см. под-алгоритм ниже)
     b. Если step.status == 'banner':
          throw ContextExhaustedError(step.banner)
        Если step.status == 'timeout':
          throw Error("Timeout")
     c. Прокрутить вниз (scrollToBottomIfNeeded).
     d. Проверить баннер ещё раз (он мог появиться во время прокрутки).
        Если есть — throw ContextExhaustedError.
     e. Проверить наличие кнопки Continue в фрагменте assistantKey.
          Если есть:
            - Кликнуть Continue.
            - Дождаться появления Stop (5 сек).
            - continue (следующая итерация)
     f. Кнопки Continue нет — ответ завершён:
          - Извлечь через Copy (B3).
          - Если Copy не сработал — fallback через markdown (B4).
          - Вернуть текст.
3. Если цикл завершился без выхода — throw Error("Max Continue iterations").
```

**Под-алгоритм waitForChunkComplete:**

```
Фаза A (0..10 сек, шаг 100 мс):
  Снимок состояния: {stop, sendDisabled, banner}
  - Если banner    → вернуть {status: 'banner'}
  - Если stop      → break в фазу B
  - Если sendDisabled && !stop накапливается ≥ 1 сек
                   → вернуть {status: 'done', trigger: 'state_persisted'}

Фаза B (до deadline, шаг 500 мс):
  Снимок состояния.
  - Если banner    → вернуть {status: 'banner'}
  - Если !stop:
      10 × с шагом 200 мс проверить:
        - banner появился → вернуть {status: 'banner'}
        - sendDisabled && !stop → вернуть {status: 'done'}
        - stop появился снова → break и продолжить ждать в фазе B
```

### Граничные случаи

- **Очень короткий ответ (Stop мелькнул между опросами).** Ловится
  через «sendDisabled && !stop накапливается ≥ 1 сек» в фазе A.
- **Длинный ответ с паузой.** Continue появляется в футере; цикл
  перезапускает ожидание, ассистентский ключ не меняется.
- **Ответ длиннее viewport.** Перед каждой проверкой футера
  вызывается `scrollToBottomIfNeeded`, иначе кнопки Continue и Copy
  могут быть не отрендерены виртуальным списком.
- **Поздний баннер длины.** Может появиться уже после исчезновения
  Stop. Проверяется дважды: в `waitForChunkComplete` и в основном
  цикле после прокрутки.
- **Превышение MAX_CONTINUE.** Исключение; клиент получит 500.

### Почему именно так

**Почему две фазы в waitForChunkComplete.** Первая версия опрашивала
только Stop. Проблема: короткие ответы завершаются так быстро,
что Stop может не появиться ни на одном опросе. Фаза A добавляет
эвристику «send disabled без Stop» — она устойчива к этому случаю.

**Почему после Stop нужно ждать ещё подтверждение sendDisabled.**
Кнопка Stop может исчезнуть за миллисекунды до того, как DeepSeek
переключит Send из disabled в enabled. Без подтверждения мы могли
бы попытаться прочитать ответ до того, как он окончательно
отрендерился.

**Почему перепроверка баннера после прокрутки.** Баннер длины
иногда появляется одновременно с исчезновением Stop. `waitForChunkComplete`
мог его не увидеть, если DOM-обновление произошло позже опроса.
Прокрутка меняет layout и вызывает перерисовку — момент удобен для
повторной проверки.

**Почему прокрутка вниз обязательна.** Виртуальный список DeepSeek
рендерит только видимые элементы. Если ответ длинный, кнопки Continue
и Copy находятся далеко внизу и в DOM могут отсутствовать. Без
прокрутки `hasContinueButton` вернёт false, и система попытается
извлечь неполный ответ.

**Почему ассистентский ключ — `lastKey + 2`.** Формат DeepSeek:
нечётные ключи — user-сообщения, чётные — assistant. После отправки
user с ключом `lastKey + 1` ассистент получит `lastKey + 2`.

**Почему MAX_CONTINUE = 20.** Эмпирическая оценка: Continuе-цикл
редко превышает 2–3 итерации, лимит 20 даёт большой запас на случай
нестандартного поведения. Бесконечный цикл заблокировал бы очередь
задач.

### Реализация

- `src/chat/ChatController.ts` → `waitForFullResponse()`,
  `waitForChunkComplete()`, `getTriggerState()`, `scrollToBottomIfNeeded()`
- `src/DeepSeekClient.ts` → `executePipeline()` (вызов)
- `src/browser/Selectors.ts` → `stopButton`, `sendButtonExists`,
  `continueButton`, `scrollToBottomButton`, `lengthLimitBannerPattern`

## B3. Извлечение ответа через Copy {#b3}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (проверка Regenerate для отличия от Copy в блоке кода)

### Назначение

Получить полный текст ассистентского ответа через клик по кнопке Copy
в футере сообщения и чтение буфера обмена.

### Входные данные

- `messageKey: number` — `data-virtual-list-item-key` ассистентского
  сообщения.
- `maxDepth: number` — максимальная глубина обхода предков (по умолчанию 3).

### Выходные данные

- `{ ok: true, text, depth }` — успех.
- `{ ok: false, reason }` — что-то не сработало.

### Псевдокод

```
1. Найти блок по data-virtual-list-item-key.
2. Найти в блоке все [role="button"], чей SVG path начинается с
   префикса Copy (M6.14929 4.02032).
3. Для каждой такой кнопки:
     node := parentElement
     depth := 0
     Пока node существует и depth <= maxDepth:
        Если в node есть кнопка с SVG path, начинающимся с Regenerate
        (M7.92136 0.349152) — эта Copy-кнопка принадлежит футеру.
           Кликнуть по ней, вернуть {ok:true, depth}.
        node := node.parentElement
        depth++
4. Если ни одна Copy-кнопка не имеет Regenerate в предках —
   вернуть {ok:false, reason:'no footer copy found'}.
5. Подождать 600 мс.
6. Прочитать буфер обмена, вернуть текст.
```

### Граничные случаи

- **Ответ содержит блок кода.** Внутри блока кода тоже есть Copy
  (для копирования кода целиком). Отличается отсутствием Regenerate
  в предках — тот Copy не пройдёт проверку.
- **Блок с ответом не найден.** Возврат `{ok:false, reason:'block not found'}`.
- **Кнопка Copy отсутствует.** Возврат `{ok:false}` — вызывающий
  код (B2) использует fallback (B4).
- **Буфер обмена пуст.** Возврат `{ok:true, text:''}`. Пустая строка
  не является валидным ответом — на верхнем уровне это будет
  распознано как «пустой ответ».

### Почему именно так

**Почему не клик по последнему Copy на странице.** Первая версия
искала все Copy на странице, кликала по последнему. Проблема:
в длинном ответе с несколькими блоками кода последний Copy мог
принадлежать блоку кода, а не сообщению. Копировался бы фрагмент
кода вместо целого ответа.

**Почему проверка через Regenerate.** В футере ассистентского
сообщения есть кнопка Regenerate. В блоках кода её нет. Это
единственный стабильный признак, отличающий Copy-сообщения от
Copy-кода.

**Почему обход предков ограничен глубиной 3.** В реальном DOM
Copy и Regenerate находятся в одном родителе (footer), но
промежуточные обёртки могут добавлять 1–2 уровня. Глубина 3 покрывает
все наблюдаемые случаи; больше — риск случайно привязать Copy из
соседнего блока.

**Почему используется буфер обмена, а не текст из DOM.** Кнопка Copy
возвращает чистый markdown-текст без визуальных артефактов (переносы,
подсветка синтаксиса, эмодзи-иконки). Из DOM это извлечь сложнее,
чем из clipboard.

### Реализация

- `src/chat/ResponseExtractor.ts` → `getCopyTextByKeyWithRegenerate()`
- `src/browser/BrowserManager.ts` → изолированный `navigator.clipboard`
- `src/browser/Selectors.ts` → `copyButtonPathPrefix`, `regenerateButtonPathPrefix`

## B4. Fallback через markdown {#b4}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (поиск по data-атрибуту вместо `:last-child`)

### Назначение

Извлечь текст ответа напрямую из DOM, если кнопка Copy не сработала
(изменился SVG-путь, кнопка отсутствует).

### Входные данные

- `messageKey: number | undefined` — ключ сообщения. Если не задан,
  берётся последнее сообщение в списке.

### Выходные данные

Текст ответа как `textContent` блока `.ds-markdown` внутри сообщения.
Пустая строка — если блок не найден.

### Псевдокод

```
1. Если messageKey задан:
     block := querySelector(`[data-virtual-list-item-key="<key>"]`)
   Иначе:
     items := все [data-virtual-list-item-key]
     block := items[items.length - 1]
2. Если block не найден — вернуть ''.
3. markdown := block.querySelector('.ds-markdown')
4. Если markdown не найден — вернуть ''.
5. Вернуть markdown.textContent, trim.
```

### Граничные случаи

- **Селектор `.ds-markdown` не срабатывает.** Возврат пустой строки.
  На верхнем уровне это приведёт к ошибке извлечения.
- **Ответ длинный и не отрендерен.** Вызывающий код (B2) прокручивает
  страницу вниз перед вызовом. Если всё равно пусто — считаем ошибкой.
- **Несколько `.ds-markdown` внутри блока.** `querySelector` вернёт
  первый. На практике в блоке сообщения он один.

### Почему именно так

**Почему не `:last-child` на `.ds-message`.** Ранняя версия искала
`.ds-message:last-child .ds-markdown` — предполагалось, что последнее
сообщение всегда last-child. На практике DeepSeek вставляет между
сообщениями служебные элементы (индикаторы, разделители), и
`:last-child` перестаёт совпадать. Поиск по data-атрибуту устойчив.

**Почему `.ds-markdown`, а не `.ds-message`.** `textContent` всего
сообщения содержит не только ответ, но и метаданные (имя модели,
timestamp, иконки действий). `.ds-markdown` — только тело ответа.

**Почему textContent, а не innerText.** `innerText` учитывает
стили и может возвращать пустую строку для скрытых или ещё не
отрендеренных блоков. `textContent` работает с DOM напрямую.

**Почему fallback включён в основной пайплайн.** В v1 он вызывался
только при `attempts > 4` в старом `DeepSeekClient.waitForFullResponse`.
После переноса на `ChatController.waitForFullResponse` вызов добавлен
при неудаче Copy (см. B2 шаг 2f). Это даёт реальный резерв, если
Copy-кнопка изменится.

### Реализация

- `src/chat/ResponseExtractor.ts` → `getResponseViaMarkdown()`
- `src/browser/Selectors.ts` → `markdownBodyRelative`

## B5. Детект баннера длины {#b5}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Обнаружить сообщение DeepSeek о достижении лимита длины — как глобально
на странице, так и внутри конкретного сообщения.

### Входные данные

- `messageKey: number | undefined` — ключ сообщения для scoped-проверки.
- Регулярное выражение `lengthLimitBannerPattern` из `Selectors`.

### Выходные данные

- `detectBanner(): string | null` — текст баннера или null.
- `detectLengthLimit(key?): { detected, percent, formulation }` —
  подробности для scoped-проверки.

### Псевдокод

```
detectBanner():
  text := document.body.textContent
  match := text.match(/Length limit reached[^\n]*/i)
  Вернуть match ? match[0] : null

detectLengthLimit(key):
  scope := (key задан ? блок по ключу : document)
  text := scope.textContent
  match := text.match(/Length limit reached[^\n]*/i)
  Если нет — вернуть {detected:false, percent:null}
  formulation := match[0]
  percent := формулировка.match(/first\s+(\d+)%/i)?.[1] → integer или null
  Вернуть {detected:true, percent, formulation}
```

### Граничные случаи

- **Баннер появляется в середине генерации.** `detectBanner` вызывается
  в `waitForChunkComplete` на каждой итерации — ловится.
- **Формулировка без процентов.** «Length limit reached. Please start
  a new chat.» — `percent = null`, но `detected = true`.
- **Формулировка с процентами.** «Length limit reached. DeepSeek can
  only read the first 75%...» — `percent = 75`.

### Почему именно так

**Почему textContent, а не innerText.** `innerText` вызывает
принудительный reflow (layout). В горячем цикле (проверка каждые
100–500 мс) это ощутимо замедляет работу.

**Почему глобальный и scoped — два метода.** Глобальный используется
для быстрого детекта на любой итерации. Scoped — при заполнении полей
`ContextExhaustedError` (см. E1), где важно знать проценты именно
из сообщения-ответа, а не из случайного места на странице.

**Почему regex включает `[^\n]*`.** Формулировка может содержать
проценты и продолжение. Регулярное выражение захватывает всю строку
до перевода строки, чтобы извлечь и процент, и полный текст.

### Реализация

- `src/chat/ResponseExtractor.ts` → `detectBanner()`, `detectLengthLimit()`
- `src/browser/Selectors.ts` → `lengthLimitBannerPattern`

## B6. Детект плашки Server Busy {#b6}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Обнаружить системную плашку «Server busy, please try again later»,
которая появляется вместо ответа модели, когда бэкенд DeepSeek
отказывает.

### Входные данные

- Список блоков `[data-virtual-list-item-key]` в DOM.
- Два сигнала: SVG-путь Retry и точный текст предупреждения.

### Выходные данные

`boolean` — присутствует ли плашка в DOM.

### Псевдокод

```
1. Для каждого блока [data-virtual-list-item-key]:
   a. Найти все svg path внутри блока.
      Если любой path начинается с retryButtonPathPrefix (M9.94076 1.34942):
        Вернуть true.
   b. Найти все span внутри блока.
      Если любой span.textContent.trim() === serverBusyText:
        Вернуть true.
2. Вернуть false.
```

### Граничные случаи

- **Пользователь сам написал эту фразу в сообщении.** Роль-проверка:
  плашка имеет другой визуальный контекст, но текст совпадает.
  SVG-путь Retry не совпадёт с пользовательским текстом — комбинированный
  детект устойчив.
- **Retry присутствует, но текст на другом языке.** Детект срабатывает
  по SVG-пути (основной сигнал), локализация не мешает.
- **Retry отсутствует, текст на английском.** Срабатывает по тексту
  (резервный сигнал).

### Почему именно так

**Почему два сигнала, а не один.** DeepSeek может изменить SVG-путь
Retry или текст предупреждения независимо. Комбинированный детект
переживает изменения одного из них.

**Почему детект внутри блоков сообщений, а не глобально.** Если искать
по всему `document.body`, слово «Server busy» может попасть в
пользовательский вопрос или в ответ модели. Scoped-поиск исключает
ложные срабатывания.

**Почему проверка вызывается только при пустом ответе.** Плашка
появляется вместо ответа. Если ответ получен — её наличие невозможно.
Проверка в `executePipeline` после пустой строки минимизирует
ложные срабатывания и избегает лишних DOM-обходов.

### Реализация

- `src/chat/ResponseExtractor.ts` → `detectServerBusy()`
- `src/browser/Selectors.ts` → `retryButtonPathPrefix`, `serverBusyText`

## B7. Обработка Server Busy → shutdown {#b7}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Прервать работу сервера, когда DeepSeek вернул плашку Server Busy.
Повторные запросы бесполезны — бэкенд отказывает часами.

### Входные данные

- Результат детекта B6 при пустом ответе.

### Выходные данные

- HTTP 503 клиенту с типом ошибки `server_busy`.
- `process.exit(1)` через 500 мс.

### Псевдокод

```
В executePipeline:
  response := полученный текст
  Если response.length == 0:
     serverBusy := detectServerBusy()
     Если serverBusy:
        Записать в лог "🚫 DeepSeek server busy — shutting down."
        throw ServerBusyError()
     Иначе:
        throw Error("Empty response from DeepSeek")

В chat.js (catch):
  Если err.name == 'ServerBusyError':
     Отправить 503 { error: { type: 'server_busy', message: ... } }
     setTimeout(() => process.exit(1), 500)
     return
```

### Граничные случаи

- **Плашка появилась, но ответ непустой.** Сценарий невозможен: плашка
  заменяет ответ. Если появилась — ответ пуст. Проверка `length === 0`
  гарантирует, что ложное срабатывание не приведёт к shutdown.
- **Пустой ответ без плашки.** Не shutdown, а обычная 500-ошибка.
  Это может быть следствие таймаута или иной проблемы.
- **Клиент оборвал соединение до 500 мс.** `process.exit(1)` всё
  равно сработает — таймер уже запланирован.

### Почему именно так

**Почему shutdown, а не retry.** Опыт показывает: после Server Busy
DeepSeek не отвечает несколько часов. Повторные попытки только
тратят ресурсы и создают нагрузку на бэкенд. Остановка сервера
передаёт решение супервизору (systemd, pm2, docker restart policy).

**Почему 500 мс перед exit.** Нужно, чтобы ответ 503 успел дойти
до клиента. Без задержки Node.js может завершиться до того, как
буфер сокета отправит байты.

**Почему статус 503, а не 500.** 503 Service Unavailable семантически
корректен: сервис временно недоступен. Клиент может использовать
`Retry-After`, хотя в нашем случае он не выставляется — таймер
неизвестен.

**Почему код выхода 1.** Ненулевой код сигнализирует об аварийном
завершении. Системные супервизоры, не настроенные на автоматический
перезапуск, оставят сервер выключенным — это ожидаемое поведение.

### Реализация

- `src/types.ts` → `ServerBusyError`
- `src/DeepSeekClient.ts` → `executePipeline()`
- `server-modules/routes/chat.js` → обработчик в `catch`
