# Очереди и синхронизация

Алгоритмы Q1–Q5 описывают сериализацию UI-задач, приоритеты,
ретраи и фоновую обработку.

---

## Q1. Сериализация UI-задач {#q1}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Гарантировать, что в любой момент времени с UI DeepSeek работает
только одна задача. Браузерная страница — единый разделяемый ресурс.

### Входные данные

- `task: Task` — задача на выполнение.
- `priority: 'high' | 'normal'`.

### Выходные данные

Promise, резолвится результатом задачи или реджектится с ошибкой
после всех ретраев.

### Псевдокод

```
add(task, priority):
  Вернуть new Promise((resolve, reject) => {
     task.setPromiseHandlers(resolve, reject)
     Если priority === 'high': highQueue.push(task)
     Иначе: normalQueue.push(task)
     process()
  })

process():
  Если running — выход (первый вызов владеет циклом).
  running := true
  Пока highQueue или normalQueue не пусты:
     task := highQueue.shift() ?? normalQueue.shift()
     try: await task.run(client)
     catch: логировать, продолжить
  running := false
```

### Граничные случаи

- **Ошибка в задаче.** Логируется, очередь продолжает работу.
- **Reentrant вызов.** Второй `process()` сразу выходит.
- **Задача добавляется во время выполнения.** Попадёт в очередь,
  обработается в текущей итерации цикла.

### Почему именно так

**Почему одна очередь, а не параллельные.** Все задачи работают с одной
страницей Playwright. Параллельный клик/ввод/чтение привёл бы к гонкам
в DOM.

**Почему `process` реентерабельно-безопасен.** `add` вызывает `process`
для каждой задачи. Без guard'а `running` второй вызов вошёл бы в цикл
параллельно и запустил задачу до завершения первой.

**Почему ошибки не останавливают очередь.** Одна упавшая задача
не должна блокировать последующие. Клиент получит reject, но сервер
продолжит работу.

### Реализация

- `src/task/TaskQueue.ts`

## Q2. Приоритеты high / normal {#q2}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Позволить срочным задачам (например, переход при переполнении)
выполняться раньше уже стоящих в очереди.

### Входные данные

- `priority: 'high' | 'normal'`.

### Выходные данные

Порядок выполнения: сначала все high, потом normal (FIFO внутри каждого).

### Псевдокод

```
process():
  task := highQueue.shift() ?? normalQueue.shift()
```

### Граничные случаи

- **Все задачи normal.** Работает как обычная FIFO.
- **High добавляется после начала выполнения normal.** Следующая
  итерация возьмёт high.
- **Много high задач.** Выполнятся в порядке добавления.

### Почему именно так

**Почему два уровня, а не N.** В проекте всего два типа срочности:
- High: задачи перехода (нужно освободить место до баннера).
- Normal: всё остальное.

Больше уровней усложнили бы код без пользы.

**Почему не вытеснение (preemption).** Текущая задача не может быть
прервана — она уже взаимодействует с UI. Прерывание оставило бы
страницу в неизвестном состоянии. High-задача ждёт завершения текущей,
но выполняется до всех остальных.

### Реализация

- `src/task/TaskQueue.ts` → `add(task, priority)`

## Q3. Ретраи задач {#q3}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Автоматически повторять задачу при транзиентных сбоях.

### Входные данные

- `maxRetries: number` (по умолчанию 1, у `SendUserMessageTask` = 0).

### Выходные данные

Результат успешной попытки или ошибка после всех ретраев.

### Псевдокод

```
Task.run(client):
  try:
     result := execute(client)
     resolve(result)
     Вернуть result
  catch error:
     Если retryCount < maxRetries:
        retryCount++
        log "Retrying..."
        Вернуть run(client)   // рекурсия
     reject(error)
     throw error
```

### Граничные случаи

- **`maxRetries = 0`.** Одна попытка, сразу reject при ошибке.
- **Успех с первой попытки.** Рекурсия не запускается.
- **Все попытки неудачны.** Reject с последней ошибкой.

### Почему именно так

**Почему рекурсия, а не цикл.** Рекурсия читается компактнее и делает
`retryCount` явным. Глубина ретраев мала (0–1), риск переполнения стека
отсутствует.

**Почему default = 1.** Большинство транзиентных сбоев (короткий
timeout DOM) проходят со второй попытки. Больше — удлиняет latency.

**Почему `SendUserMessageTask.maxRetries = 0`.** Отправка сообщения
не идемпотентна: повторная отправка создаст дубликат в чате. Для этой
задачи ретрай опаснее, чем полезен.

### Реализация

- `src/task/Task.ts` → `run()`

## Q4. Фоновые CPU-задачи (индексация) {#q4}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Выполнять CPU-bound эмбеддинг вне request-response цикла.

### Входные данные

- `IndexingJob`: `{ filePath, apiKey, chatId, fileName }`.

### Выходные данные

Индексированные фрагменты в `HistoryStore` соответствующей сессии.

### Псевдокод

См. R6.

### Граничные случаи

- **Длинный файл (минуты CPU).** Worker не блокирует HTTP-запросы,
  они возвращаются сразу.
- **Одновременный доступ к `HistoryStore`.** Worker и HTTP-поток могут
  писать/читать индекс. Используется promise `ready` в `HistoryStore`.

### Почему именно так

**Почему отдельный worker, а не `setImmediate`/`setTimeout`.** Очередь
с одним worker даёт FIFO и естественно ограничивает параллелизм.
`setImmediate` запустил бы N эмбеддингов одновременно, что бессмысленно
на одном CPU.

**Почему job не персистится.** Индексация — оптимизация, не критичные
данные. Если процесс упадёт, файл не проиндексируется; при следующей
загрузке того же файла задача встанет заново.

**Почему файлы удаляются после обработки.** Временные загрузки не
должны накапливаться. `enqueue` передаёт владение файлом очереди.

### Реализация

- `src/rag/IndexingQueue.ts`

## Q5. Корректное завершение фоновых задач {#q5}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

При shutdown сервера дождаться текущей индексации (с таймаутом) и
удалить файлы незапущенных задач.

### Входные данные

- `timeoutMs: number` (по умолчанию 60000).

### Выходные данные

Текущая задача завершена (или abandoned), очередь пуста.

### Псевдокод

```
shutdown(timeoutMs):
  shutdownRequested := true
  deadline := now + timeoutMs
  Пока busy и now < deadline:
     wait 200ms
  Если busy: логировать "timeout, abandoning"

  pending := queue.length
  Если pending > 0: логировать
  Для каждого job из queue: deleteFile(job.filePath)
  queue := []
```

### Граничные случаи

- **Текущая задача завершилась быстро.** Ожидание короткое.
- **Текущая задача висит > 60 секунд.** Abandoned, но файл будет
  удалён при завершении (в `finally` внутри `process`).
- **Очередь пуста.** Сразу выход.

### Почему именно так

**Почему ждём текущую задачу, а не убиваем.** Эмбеддинг — атомарная
операция; прерывание посередине может оставить индекс в неконсистентном
состоянии (записана часть чанков). Лучше дождаться.

**Почему 60 секунд.** Большинство файлов индексируются за секунды.
60 секунд — щедрый запас на крупный файл в конце очереди. Если
не уложились — файл потеряется, но сервер завершится.

**Почему файлы pending удаляются.** Они уже не будут обработаны.
Оставленные на диске, они накопятся при каждом перезапуске.

### Реализация

- `src/rag/IndexingQueue.ts` → `shutdown()`
- `server.js` → `SIGINT` / `SIGTERM`
