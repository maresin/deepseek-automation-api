# Управление контекстом

Алгоритмы C1–C7 описывают отслеживание размера контекста,
динамический лимит, пороговые срабатывания и работу со снапшотами.

---

## C1. Анализ языка и языковой коэффициент {#c1}
**Статус:** active
**Дата фиксации:** 2026-09-19
**Версия:** 2 (коэффициент кириллицы откалиброван: 2.3 → 2.4)

### Назначение

Определить языковой состав пользовательских сообщений и вывести
коэффициент «символов на токен», чтобы скорректировать эффективный
лимит контекста.

### Входные данные

- Первые пользовательские сообщения, накопленные в `userTextBuffer`.
- Пороги: `MIN_ANALYSIS_CHARS = 500`, `MAX_ANALYSIS_CHARS = 5000`.

### Выходные данные

- Объект `languageMix` с долями {latin, cyrillic, cjk, other}.
- Метод `getLanguageCoefficient()` возвращает число в диапазоне 1.0–3.0.

### Псевдокод

```
analyzeUserMessage(text):
  Если анализ уже выполнен — выход.
  userTextBuffer += text
  Если userTextBuffer.length >= 500:
     sample := первые 5000 символов
     Для каждого символа sample:
        Пропустить пробелы, пунктуацию, ASCII-разделители.
        Классифицировать: CJK / Cyrillic / Latin / Other.
     languageMix := нормализованные доли
     languageAnalysisDone := true

getLanguageCoefficient():
  Если анализ не проводился — вернуть 2.5 (средняя оценка).
  Вернуть w.latin*3.0 + w.cyrillic*2.4 + w.cjk*1.0 + w.other*2.0
```

### Языковые коэффициенты

| Язык | Коэффициент | Токенов на символ | Источник |
|---|---|---|---|
| Латиница | 3.0 | 0.3 | Официальное соотношение DeepSeek |
| Кириллица | 2.4 | 0.42 | Эмпирическая калибровка (см. ниже) |
| CJK | 1.0 | 0.6 | Официальное соотношение DeepSeek |
| Прочее | 2.0 | ~0.5 | Промежуточное значение |

### Почему именно такие коэффициенты

**Почему кириллица — 2.4, а не расчётные 2.38 (1M / 0.42).**
Значение получено эмпирически на реальном UI DeepSeek. Официальный
коэффициент 0.42 токена на символ даёт ~2 380 952 символов, но реальная
точка срабатывания баннера — 2 400 000. Разница объясняется тем, что
кириллический текст в сессии содержит вкрапления латиницы (код, URL,
термины), и DeepSeek считает смешанный текст иначе, чем чистую кириллицу.
Версия 1 использовала 2.3 — это давало консервативный запас, но
переход срабатывал раньше, чем нужно. Версия 2 использует 2.4 —
калибровка по факту.

**Почему латиница — 3.0, а не расчётные 3.33 (1M / 0.3).**
3 333 333 символа × 0.3 = 1 000 000 токенов — ровно лимит. Но в реальной
сессии к пользовательскому тексту добавляются роли, служебные токены,
разметка — всё это съедает часть окна. 3 000 000 даёт запас ~10%,
который на практике оказывается достаточным.

**Почему CJK — 1.0, а не расчётные 1.67 (1M / 0.6).**
CJK-символы токенизируются плотнее всего, но реальный CJK-текст
содержит латиницу (код, имена, URL) и цифры, которые токенизируются
реже. 1 000 000 — консервативная оценка, дающая запас 40%.

**Почему 500–5000 символов для анализа.** До 500 символов статистика
неустойчива. Свыше 5000 — растёт стоимость парсинга на каждом сообщении.
Диапазон выбран эмпирически: он даёт стабильное распределение для
типичного диалога из 2–3 реплик.

**Почему один раз за сессию.** Язык пользователя редко меняется посреди
чата. Повторный анализ только тратит CPU.

### Граничные случаи

- **Текст короче 500 символов.** Анализ не запускается, коэффициент 2.5.
- **Пустой текст.** `analyzeUserMessage` немедленно выходит.
- **Смешанный текст.** Доли суммируются к 1, коэффициент — взвешенное среднее.
- **Только CJK.** Коэффициент 1.0, лимит 1 000 000.

### Реализация

- `src/context/ContextManager.ts` → `analyzeUserMessage()`, `getLanguageCoefficient()`

### История

- v1 (2026-09-18): коэффициент кириллицы 2.3.
- v2 (2026-09-19): коэффициент кириллицы 2.4 — эмпирическая калибровка.

## C2. Динамический лимит контекста {#c2}
**Статус:** active
**Дата фиксации:** 2026-09-19
**Версия:** 2 (добавлены параметры модели и обоснование лимитов)

### Назначение

Вычислить эффективный лимит символов, исходя из языкового коэффициента
и контекстного окна текущей модели.

### Входные данные

- `DEEPSEEK_MAX_CONTEXT_CHARS` из `.env` (fallback, по умолчанию 2 400 000).
- Языковой коэффициент из C1.

### Выходные данные

Число — максимум символов, при котором DeepSeek ещё не выдаёт баннер.

### Параметры модели

Лимиты калиброваны под **DeepSeek-V4.1-Flash** (текущая модель Web-версии):

| Параметр | Значение |
|---|---|
| Контекстное окно | 1 048 576 токенов (≈1M) |
| Максимальный вывод | 384 000 токенов |
| Ввод | Текст + изображения |
| Параметров (всего / активных) | 552B / 8B (вход), 16B (выход) |

### Псевдокод

```
getDynamicMaxChars():
  Если анализ языка не проводился — вернуть maxChars (2_400_000).
  coefficient := getLanguageCoefficient()
  Вернуть 1_000_000 * coefficient
```

### Эмпирические лимиты

| Язык | Коэффициент | Лимит символов | Токенов (оценка) |
|---|---|---|---|
| Латиница | 3.0 | 3 000 000 | 900 000 |
| Кириллица | 2.4 | 2 400 000 | ~1 008 000 |
| CJK | 1.0 | 1 000 000 | 600 000 |

Чистых языков в сессиях не бывает — коэффициент смешивается
пропорционально долям символов.

### Граничные случаи

- **Латиница.** Коэффициент 3.0 → лимит 3 000 000 символов.
- **CJK.** Коэффициент 1.0 → лимит 1 000 000 символов.
- **Смесь.** Промежуточное значение.
- **До первого анализа.** Fallback 2 400 000.

### Почему именно так

**Почему 1 000 000 как база.** DeepSeek оперирует токенами; один
токен ≈ 1 символу CJK ≈ 2.4 кириллицы ≈ 3 латиницы. База 1 000 000 —
оценка среднего числа токенов до баннера. Умножение на коэффициент
переводит её в символы конкретного пользователя.

**Почему не жёсткий лимит из .env.** Фиксированный `DEEPSEEK_MAX_CONTEXT_CHARS`
остаётся как fallback (до первого анализа) и как верхняя граница
безопасности. Но реальный лимит зависит от языка — при латинице он
может быть в три раза выше.

**Почему не используем полное окно 1 048 576.** В реальной сессии
к пользовательскому тексту добавляются: system-промпт, служебные
токены, разметка сообщений, история ролей. Всё это съедает часть окна.
База 1 000 000 даёт ~5% запас.

**Почему расчётный лимит может не совпадать с реальным.** Мы считаем
символы, DeepSeek — токены. Соотношение зависит от типа текста.
Точность ±20% — норма. Реальный лимит появляется в ответе только
при баннере (`deepseek_length_limit.readable_percent`). См.
[Управление сессией](../guides/session-management.md).

### Реализация

- `src/context/ContextManager.ts` → `getDynamicMaxChars()`

### История

- v1 (2026-09-18): базовая формула, коэффициент кириллицы 2.3.
- v2 (2026-09-19): коэффициент кириллицы 2.4, добавлены параметры
  модели V4.1 Flash и обоснование эмпирических лимитов.

## C3. Пороговые срабатывания (70% / 90%) {#c3}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (пороги разделены на независимые снимки)

### Назначение

Решить, когда создавать снапшот и когда начинать авто-переход в новый чат.

### Входные данные

- `totalChars` — текущий размер контекста.
- Флаги `snapshot70Done`, `snapshot90Done`.
- `ENABLE_SNAPSHOT`, `ENABLE_RAG`.

### Выходные данные

- Возможно создание или перезапись снапшота.
- Установка `needTransition = true` при 90%.

### Псевдокод

```
checkAndSnapshot():
  Если оба режима (SNAPSHOT и RAG) выключены — выход.

  percent := totalChars / getDynamicMaxChars() * 100

  Если ENABLE_SNAPSHOT:
     Если percent >= 90 и !snapshot90Done:
        createTransitionSnapshot()
     Иначе если percent >= 70 и !snapshot70Done:
        createSessionSnapshot()

  Если percent >= 90:
     needTransition := true
```

### Граничные случаи

- **Первый запрос сразу превышает 90%.** Создаётся transition-снапшот,
  snapshot_70 пропускается.
- **SNAPSHOT выключен, RAG включён.** Снапшоты не создаются, но
  `needTransition` устанавливается — при переходе RAG активируется.
- **Повторный вызов после срабатывания.** Флаги не дают пересоздать снапшот.

### Почему именно так

**Почему два порога, а не один.** 70% — мягкий порог: снапшот готовится
заранее, чтобы к моменту 90% он уже был. 90% — жёсткий: пора переходить.
Если бы порог был один, снапшот либо создавался слишком поздно (риск
не успеть), либо слишком рано (дорого).

**Почему flags, а не проверка «файл существует».** Файл может быть удалён
внешним процессом. Флаги живут в `chat_state.json` и переживают перезапуск.

**Почему transition-флаг ставится при 90% даже без SNAPSHOT.** При
активированном RAG переход нужен, чтобы открыть новый чат и включить
поиск по старому индексу. Снапшот тут не требуется.

### Реализация

- `src/context/ContextManager.ts` → `checkAndSnapshot()`

## C4. Создание снапшота {#c4}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Сжать текущую беседу в структурированный Markdown-документ, который
можно загрузить в новую сессию как вложение.

### Входные данные

- `prompts/snapshot_prompt.txt` — инструкция для модели.
- Лимит размера: `maxChars * 0.1`.

### Выходные данные

Файл `uploads/snapshot.txt` (или ошибка, если модель вернула пустоту).

### Псевдокод

```
createSessionSnapshot():
  Если snapshot70Done — выход.
  isCreatingSnapshot := true

  snapshotPrompt := loadPrompt('snapshot_prompt.txt')
  wasDeepThink := isDeepThinkEnabled()
  Если !wasDeepThink: setDeepThink(true)

  content := executePipeline({ text: snapshotPrompt, skipStatsUpdate: true })

  Если !wasDeepThink: setDeepThink(false)

  Если content пуст: логировать ошибку, выйти.
  Если content.length > maxChars * 0.1: обрезать.

  Записать uploads/snapshot.txt
  snapshot70Done := true
```

### Граничные случаи

- **Модель вернула пустоту.** Снапшот не создаётся, флаг не ставится.
  При следующем запросе будет новая попытка.
- **Модель вернула слишком длинный текст.** Обрезается до 10% от лимита,
  чтобы снапшот при загрузке не съел сразу весь новый контекст.
- **DeepThink уже включён.** Не переключается, восстанавливать не нужно.

### Почему именно так

**Почему через DeepThink.** Снапшот — это операция на длинном контексте.
DeepThink даёт более полное и точное summary. Включение и выключение
обёрнуто в try/finally, чтобы не оставить режим включённым при ошибке.

**Почему `skipStatsUpdate: true`.** Промпт снапшота и ответ модели —
служебные, они не должны увеличивать счётчик `totalChars` текущего чата.
Снапшот будет загружен в **новом** чате, там счётчик начнётся с нуля.

**Почему 10% от лимита.** Снапшот загружается в новый чат первым
сообщением. Он должен занимать разумную долю, оставляя место для
продолжения работы. 10% — компромисс: достаточно деталей, но не блокирует
новую сессию.

### Реализация

- `src/context/ContextManager.ts` → `createSessionSnapshot()`
- `prompts/snapshot_prompt.txt`

## C5. Перезапись снапшота на 90% {#c5}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Обновить снапшот более свежим содержимым перед переходом в новый чат.

### Входные данные

- `snapshot_prompt.txt`.
- Файл `uploads/snapshot.txt` (существующий, от 70%).

### Выходные данные

Обновлённый `uploads/snapshot.txt` с флагами `snapshot70Done = true`,
`snapshot90Done = true`.

### Псевдокод

```
createTransitionSnapshot():
  isCreatingSnapshot := true
  snapshotPrompt := loadPrompt('snapshot_prompt.txt')
  wasDeepThink := isDeepThinkEnabled()
  Если !wasDeepThink: setDeepThink(true)

  content := executePipeline({ text: snapshotPrompt, skipStatsUpdate: true })

  Если !wasDeepThink: setDeepThink(false)
  Если content пуст: вернуть null (файл не перезаписан).

  Обрезать до maxChars * 0.1.
  Записать uploads/snapshot.txt (перезапись).
  snapshot70Done := true
  snapshot90Done := true
  Вернуть путь к файлу.
```

### Граничные случаи

- **Снапшота от 70% нет.** Перезапись создаёт файл с нуля, флаг 70%
  выставляется принудительно.
- **Пустой ответ модели.** Старый снапшот сохраняется, transition
  продолжится с ним. Хуже, чем свежий, но лучше, чем ничего.

### Почему именно так

**Почему не удалять старый снапшот до получения нового.** Если модель
вернёт пустоту или упадёт, старый снапшот останется единственным
носителем контекста. Удаление сначала — потеря данных.

**Почему флаг 90% выставляется даже при успехе с первого раза.**
`createTransitionSnapshot` вызывается напрямую, минуя `createSessionSnapshot`,
если контекст сразу перескочил 70%. Без явного флага 70% следующий
вызов `checkAndSnapshot` попытался бы создать снапшот заново.

### Реализация

- `src/context/ContextManager.ts` → `createTransitionSnapshot()`

## C6. Очистка снапшота после перехода {#c6}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Удалить снапшот-файл и сбросить оба флага после успешной загрузки в новый чат.

### Входные данные

- Файл `uploads/snapshot.txt`.
- Флаги `snapshot70Done`, `snapshot90Done`.

### Выходные данные

Файл удалён, флаги сброшены в `false`.

### Псевдокод

```
clearSnapshot():
  Если файл существует — удалить.
  snapshot70Done := false
  snapshot90Done := false
```

### Граничные случаи

- **Файл отсутствует.** Удаление пропускается, флаги сбрасываются.
- **Ошибка удаления (permissions).** Логируется предупреждение,
  флаги всё равно сбрасываются.

### Почему именно так

**Почему флаги сбрасываются даже при ошибке удаления.** Флаги и файл
семантически связаны, но флаг — это «снапшот уже использован». Даже если
файл остался на диске, следующий цикл (70% → 90%) создаст его заново,
перезаписав старый.

**Почему вызывается в двух местах.** После `handleOverflow` (при загрузке
в новый чат) и при `startFresh` (полный сброс сессии). Единая функция
гарантирует согласованное состояние.

### Реализация

- `src/context/ContextManager.ts` → `clearSnapshot()`
- `src/DeepSeekClient.ts` → `handleOverflow()`, `startFresh()`

## C7. Оценка размера запроса (totalChars) {#c7}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (учёт множителя DeepThink)

### Назначение

Увеличить счётчик `totalChars` после успешного запроса, чтобы отслеживать
приближение к лимиту.

### Входные данные

- `text.length` — длина отправленного промпта.
- `response.length` — длина ответа модели.
- `filePaths` — список загруженных файлов (если есть).
- `multiplier` — множитель от DeepThink (`DEEPSEEK_DEEPTHINK_MULTIPLIER`,
  по умолчанию 2.5).

### Выходные данные

Обновлённый `totalChars`, запись в `chat_state.json`.

### Псевдокод

```
addChars(addedChars, multiplier=1):
  effectiveChars := floor(addedChars * multiplier)
  totalChars += effectiveChars
  saveChatState()
```

В `executePipeline`:
```
addedChars := text.length + response.length
Если filePath: добавить размер не-изображений.
Если DeepThink включён: multiplier := 2.5 (или из .env).
addChars(addedChars, multiplier)
```

### Граничные случаи

- **DeepThink выключен.** Множитель 1.
- **Изображение в files.** Пропускается — изображения оцениваются
  отдельно через `IMAGE_TOKENS` в `FileUploader`.
- **Ошибка чтения файла.** Логируется, размер не добавляется.

### Почему именно так

**Почему множитель для DeepThink.** Внутренние рассуждения R1 не попадают
в итоговый ответ, но потребляют контекст. Без множителя система
недооценивает реальный расход и переходит в новый чат слишком поздно —
пользователь получает неожиданный баннер.

**Почему `2.5` по умолчанию.** Эмпирическая оценка: R1 генерирует
примерно в 2.5 раза больше токенов, чем видно в финальном ответе.
Значение вынесено в `.env` для калибровки.

**Почему `saveChatState` вызывается сразу.** Счётчик должен пережить
перезапуск сервера. Без сохранения после перезапуска контекст обнулится,
и система потеряет позицию в цикле 70/90.

### Реализация

- `src/context/ContextManager.ts` → `addChars()`
- `src/DeepSeekClient.ts` → `executePipeline()`
