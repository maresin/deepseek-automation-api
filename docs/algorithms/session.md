# Управление сессией

Алгоритмы A1–A6 описывают жизненный цикл сессии:
от инициализации клиента до перехода в новый чат и сохранения состояния.

---

## A1. Инициализация клиента {#a1}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Открыть браузер, пройти аутентификацию, подготовить страницу DeepSeek
к работе и восстановить или начать сессию.

### Входные данные

- `config.headless: boolean` — режим отображения браузера.
- `config.email / config.password: string | undefined` — учётные данные.
- `config.statePath: string` — путь к `state.json` с cookies.
- Переменная окружения `ENABLE_RESTORE: 'true' | 'false'`.

### Выходные данные

- Готовый к работе `DeepSeekClient` с открытой страницей.
- Созданный или восстановленный чат.

### Псевдокод

```
1. Если клиент уже инициализирован — выход.
2. Прочитать state.json (cookies браузера).
3. Запустить Chromium, открыть контекст с сохранёнными cookies.
4. Если cookies есть — открыть chat.deepseek.com.
   Иначе — /sign_in.
5. Пройти аутентификацию (см. AuthManager.ensureAuthenticated).
6. Сохранить обновлённое состояние в state.json.
7. Проверить язык интерфейса (см. A3.5, ensureEnglishLanguage).
8. Если ENABLE_RESTORE=true:
     попытаться восстановить последнюю сессию (A2);
     если не удалось — начать новую (A3).
   Иначе — начать новую.
9. Пометить клиент как готовый.
```

### Граничные случаи

- **Cookies отсутствуют и нет credentials в `.env`.** AuthManager ждёт
  ручного логина до 2 минут. Если пользователь не логинится — падение.
- **Cookies отсутствуют и есть credentials.** Выполняется авто-логин.
  Если форма не найдена — исключение, клиент не инициализируется.
- **Файл `state.json` повреждён.** `loadState` возвращает пустое состояние,
  клиент идёт по ветке «нет cookies» → авто-логин или ручной.
- **Язык интерфейса не английский.** Осуществляется попытка переключения
  через Settings → General → Language. Если не удаётся — продолжает
  работу с текущим языком (селекторы могут не сработать, но падения нет).

### Почему именно так

**Почему `state.json` отделён от `chat_state.json`.** `state.json` содержит
cookies Playwright, `chat_state.json` — id чата и счётчики. Раньше они
жили вместе, но `validateEnvironment` (в `server.js`) перезаписывает
`state.json` после каждой стартовой проверки — и стирал бы `chat_state`.
Разделение файлов устраняет конфликт.

**Почему восстановление — до полной инициализации.** `restorePrevious`
опирается на доступность страницы чата. Если страница не готова —
восстановление не сработает. Порядок шагов жёсткий.

### Реализация

- `src/DeepSeekClient.ts` → `initialize()`
- `src/auth/AuthManager.ts` → `ensureAuthenticated()`

## A2. Восстановление предыдущей сессии {#a2}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Открыть последний чат, который использовался до перезапуска сервера,
и восстановить все счётчики состояния.

### Входные данные

- `chat_state.json` → поле `deepseek.lastChatId: string | null`.
- Дополнительные поля: `chatStarted`, `totalChars`, `ragSearchActive`,
  `snapshot70Done`, `snapshot90Done`.

### Выходные данные

- Объект `RestoreResult`:
  - `{ ok: true }` — сессия восстановлена.
  - `{ ok: false, reason: 'no_last_chat_id' }` — нет сохранённого id.
  - `{ ok: false, reason: 'chat_not_found' }` — чат удалён из сайдбара.

### Псевдокод

```
1. Прочитать chat_state.json.
2. Если lastChatId пуст — вернуть no_last_chat_id.
3. Проверить наличие чата в сайдбаре (chatExists).
4. Если нет — очистить chat_state.json, вернуть chat_not_found.
5. Кликнуть по ссылке чата (restoreChatById).
6. Восстановить в памяти: currentChatId, chatStarted,
   ragSearchActive, totalChars, snapshot70Done, snapshot90Done.
7. Сбросить флаги: needTransition, lastLengthLimit, systemPromptsSent.
8. Вернуть ok:true.
```

### Граничные случаи

- **Чат существует в state, но удалён из DeepSeek.** `chatExists`
  вернёт false → чат не найден → состояние очищено, начнётся новая сессия.
- **Сайдбар свёрнут.** `chatExists` не найдёт ссылку. Решение:
  `ensureSidebarExpanded` вызывается до `chatExists`.
- **state.json содержит chatId, но чат пустой (без сообщений).**
  Восстанавливается нормально, `chatStarted` может быть `false`.

### Почему именно так

**Почему восстанавливаем по `lastChatId`, а не по «первой ссылке в сайдбаре».**
Ранняя реализация кликала по первой ссылке — это работало, пока
DeepSeek не начал переупорядочивать историю по времени последнего
использования. Теперь «первая» может оказаться не той, что нужно.
Точный id устраняет неоднозначность.

**Почему `chat_not_found` ведёт к очистке состояния.** Иначе клиент
будет пытаться восстановить несуществующий чат при каждом старте.
Очистка — единственный способ выйти из цикла.

### Реализация

- `src/DeepSeekClient.ts` → `restorePrevious()`
- `src/chat/ChatController.ts` → `chatExists()`, `restoreChatById()`

## A3. Начало новой сессии {#a3}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (объединена с очисткой RAG-индекса)

### Назначение

Открыть новый чат, сбросить состояние и очистить RAG-индекс.

### Входные данные

- Не требуется. Метод идемпотентен.

### Выходные данные

- Новый чат открыт.
- `chat_state.json` содержит пустые значения.
- RAG-индекс (если RAG включён) очищен.

### Псевдокод

```
1. Очистить persistent state (chat_state.json) — все поля в default.
2. Открыть новый чат в UI.
3. Получить и сохранить currentChatId.
4. Сбросить в памяти: chatStarted, ragSearchActive, needTransition,
   lastLengthLimit, systemPromptsSent, language mix, totalChars.
5. Удалить snapshot-файл (если есть).
6. Если ENABLE_RAG=true — очистить RAG-индекс для текущего apiKey.
7. Сохранить chat_state.json.
```

### Граничные случаи

- **RAG выключен.** Шаг 6 пропускается.
- **apiKey = 'default' (клиент ещё не зарегистрирован).** Шаг 6
  пропускается — очищать нечего.
- **Файл snapshot отсутствует.** `clearSnapshot()` безопасно
  обрабатывает отсутствие файла.

### Почему именно так

**Почему очистка RAG-индекса здесь.** До версии 2 этот шаг отсутствовал:
пользователь мог вызвать `/v1/chat/new {restore: false}`, ожидая начать
новую тему, а старые данные из предыдущей оставались в индексе. При
следующем поиске всплывали чужеродные фрагменты. Очистка согласована
с семантикой «начать всё с нуля».

**Почему через `clearHistoryStoreIfExists`, а не через `store.clear()`.**
`store.clear()` требует загрузки embedding-модели (несколько секунд).
`clearHistoryStoreIfExists` умеет работать и без неё — просто
truncate файла. Это критично на старте сервера.

**Почему начало новой сессии вызывается и при старте, и по API.**
Единая точка — гарантирует, что после любого пути (инициализация,
`restore:false`, `restore` провалился) состояние консистентно.

### Реализация

- `src/DeepSeekClient.ts` → `startFresh()`
- `src/rag/init.ts` → `clearHistoryStoreIfExists()`

## A4. Авто-переход при переполнении {#a4}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (переработана при разделении snapshot / RAG)

### Назначение

Перенести диалог в новый чат, не разрывая контекст для пользователя,
когда текущий чат приближается к лимиту DeepSeek.

### Входные данные

- Флаг `needTransition: boolean` в клиенте.
- `ENABLE_SNAPSHOT: 'true' | 'false'`.
- `ENABLE_RAG: 'true' | 'false'`.
- Наличие `snapshot.txt` в `uploads/`.

### Выходные данные

- Новый чат, содержащий либо снапшот, либо (при RAG) только активированный флаг `ragSearchActive`.
- Сброшенные флаги `needTransition`, `lastLengthLimit`, снапшот-флаги.

### Псевдокод

```
1. Если ни ENABLE_SNAPSHOT, ни ENABLE_RAG не включены — выход, возврат false.
2. Взять путь к snapshot-файлу (если ENABLE_SNAPSHOT).
3. Открыть новый чат.
4. Сбросить в памяти флаги, счётчики, промпты, язык.
5. Если ENABLE_SNAPSHOT и файл существует:
     a. Загрузить snapshot как файл в новый чат.
     b. Дождаться ответа модели (использует executePipeline).
     c. Удалить файл снапшота.
6. Если ENABLE_RAG — выставить ragSearchActive = true.
7. Сохранить chat_state.json.
8. Вернуть true.
```

### Граничные случаи

- **SNAPSHOT включён, но файла нет.** Переход выполняется без снапшота,
  в лог пишется предупреждение. Контекст для пользователя потерян,
  но цикл не зациклится.
- **RAG включён, SNAPSHOT выключен.** Переход без файла, включается
  `ragSearchActive` — следующий поиск будет работать по старому индексу.
- **Оба включены.** Сначала файл снапшота, затем `ragSearchActive = true`.
- **Ошибка при загрузке снапшота.** Исключение пролетает наверх; флаги
  уже сброшены, новый чат открыт. Следующий запрос начнётся в новом чате.

### Почему именно так

**Почему снапшот загружается как файл, а не текстом в промпте.**
Модель относится к тексту в промпте как к потенциальной инъекции.
Файл через UI — реальное вложение, модель доверяет ему. Это стало
очевидно после серии экспериментов: вставка содержимого в `userText`
приводила к ответам «файла нет в беседе».

**Почему snapshot_70 и snapshot_90 — один файл.** В v1 было два файла,
что порождало вопросы «какой использовать». Один файл с перезаписью:
на 70% создаётся, на 90% обновляется более свежим содержимым. При
переходе используется актуальная версия.

**Почему сброс всех флагов до загрузки снапшота.** После `newChat`
мы уже в новом чате; если что-то пойдёт не так при загрузке — состояние
всё равно должно соответствовать новому чату.

**Почему не рекурсивный ретрай.** Раньше после перехода задача
вызывала себя заново. Это работало, но приводило к цепочке вызовов
и сложной логике счётчиков. Текущее решение: `SendUserMessageTask`
проверяет `needTransition` **до** отправки сообщения и выполняет
переход, если нужно. Исходное сообщение отправляется в новый чат
естественным путём.

### Реализация

- `src/DeepSeekClient.ts` → `handleOverflow()`
- `src/tasks/SendUserMessageTask.ts` → проверка `needTransition` в начале `execute()`
- `prompts/snapshot_upload_prompt.txt` — сопроводительный текст

## A5. Восстановление чата по ID {#a5}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Перейти в конкретный чат по его идентификатору, проверив его наличие.

### Входные данные

- `chatId: string` — идентификатор чата (UUID).

### Выходные данные

- `chatExists(chatId): Promise<boolean>` — есть ли ссылка на чат в сайдбаре.
- `restoreChatById(chatId): Promise<boolean>` — успешно ли выполнен переход.

### Псевдокод

```
chatExists(chatId):
  1. Развернуть сайдбар (если свёрнут).
  2. Найти ссылку a[href*="/a/chat/s/<chatId>"].
  3. Вернуть true, если найдена.

restoreChatById(chatId):
  1. Найти ссылку.
  2. Если не найдена — вернуть false.
  3. Кликнуть по ссылке.
  4. Дождаться появления textarea.
  5. Вернуть true.
```

### Граничные случаи

- **Сайдбар свёрнут.** Ссылки не в DOM. Решение — `ensureSidebarExpanded`
  вызывается неявно через `chatExists` / `restoreChatById`.
- **Чат удалён из DeepSeek.** Ссылки нет, возвращается false.
  Вызывающий (см. A2) очищает состояние.

### Почему именно так

**Почему не через URL-навигацию `page.goto`.** Прямой переход по URL
работает, но не обновляет визуальную историю сайдбара в SPA. Клик
по ссылке — более «естественный» путь, избегает гонок с роутером.

### Реализация

- `src/chat/ChatController.ts` → `chatExists()`, `restoreChatById()`

## A6. Хранение и загрузка состояния {#a6}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (разделение state.json / chat_state.json)

### Назначение

Разделить браузерное состояние (cookies) и состояние чата (id, счётчики)
на два файла, чтобы их жизненные циклы не пересекались.

### Входные данные

- `state.json` — cookies и origins (Playwright).
- `chat_state.json` — блок `deepseek` со следующими полями:
  - `lastChatId: string | null`
  - `chatStarted: boolean`
  - `totalChars: number`
  - `ragSearchActive: boolean`
  - `snapshot70Done: boolean`
  - `snapshot90Done: boolean`

### Выходные данные

- `saveChatState()` — запись в `chat_state.json`.
- `loadChatState()` — чтение блока `deepseek`.

### Псевдокод

```
saveChatState():
  Собрать объект из текущих полей клиента и ContextManager.
  Записать в chat_state.json (JSON, отформатированный).

loadChatState():
  Если chat_state.json существует — прочитать блок deepseek.
  Иначе — попробовать прочитать legacy-блок deepseek из state.json
    (миграция с v1).
  Вернуть null, если оба источника пусты.
```

### Граничные случаи

- **chat_state.json повреждён.** `loadChatState` возвращает null.
  Это равносильно «нет сохранённого чата» → `startFresh`.
- **Legacy-блок в state.json.** Прочитан, но при следующей записи
  `saveChatState` создаст chat_state.json; старый блок в state.json
  останется мусором до следующей очистки. Это допустимо.

### Почему именно так

**Почему разделение.** В v1 все данные хранились в state.json. Но
`server.js` в `validateEnvironment` перезаписывает state.json после
проверки селекторов — и стирал chat_state. Разделение устранило
конфликт без правки `validateEnvironment`.

**Почему legacy-миграция.** Обновление на существующей установке не
должно ломать данные. Если пользователь перезапускает сервер со старым
state.json, `loadChatState` подхватит legacy-блок, а первый
`saveChatState` перенесёт данные в новый формат.

### Реализация

- `src/DeepSeekClient.ts` → `saveChatState()`, `loadChatState()`,
  `clearPersistentState()`
- `server-modules/utils.js` → пути файлов, `deleteSessionFiles()`
- `server-modules/clientConfig.js` → `statePath`, `chatStatePath`
