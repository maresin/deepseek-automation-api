# RAG (Retrieval-Augmented Generation)

Алгоритмы R1–R8 описывают индексацию, поиск и инъекцию фрагментов
из предыдущих сессий в текущий запрос.

---

## R1. Чанкование текста {#r1}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Разбить текст на фрагменты, каждый из которых помещается в лимит
embedding-модели (Xenova/all-MiniLM-L6-v2, 512 токенов).

### Входные данные

- `text: string` — текст (файл или диалог).
- `RAG_CHUNK_SIZE` из `.env` (по умолчанию 2000).

### Выходные данные

`string[]` — массив фрагментов, каждый не длиннее `chunkSize`.

### Псевдокод

```
chunkText(text):
  chunkSize := RAG_CHUNK_SIZE (2000)
  chunks := []
  Для i = 0; i < text.length; i += chunkSize:
     chunks.push(text.slice(i, i + chunkSize))
  Вернуть chunks
```

### Граничные случаи

- **Пустой текст.** Возвращается пустой массив.
- **Текст длиннее лимита модели.** Разрезается равномерно по символам.
- **Юникод.** Разрез по кодовым единицам, не по байтам — корректно для
  большинства языков.

### Почему именно так

**Почему фиксированный размер в символах, а не по словам/предложениям.**
Модель имеет жёсткий лимит токенов. Символьный разрез даёт детерминированную
верхнюю границу независимо от языка. Разрез по словам может случайно
создать фрагмент с длинным словом, превышающим лимит.

**Почему 2000 символов.** Модель принимает 512 токенов. Для латиницы
2000 символов ≈ 600–700 токенов — с запасом. Меньше — слишком много
фрагментов (растёт стоимость хранения). Больше — риск обрезки.

**Почему без overlap.** Перекрытие даёт лучшую семантическую связность,
но удваивает объём индекса. Для нашего сценария (поиск фрагментов
по ключевым темам) потери на границах несущественны.

### Реализация

- `server-modules/chunking.js` → `chunkText()`
- `src/rag/HistoryStore.ts` → `chunkText()`

## R2. Эмбеддинг и хранение {#r2}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Преобразовать текстовый фрагмент в вектор и сохранить его в локальном
индексе вместе с метаданными.

### Входные данные

- `text: string` — фрагмент.
- `chatId: string | null` — привязанный чат.
- `type: 'exchange' | 'file'` — тип записи.

### Выходные данные

Новая запись в `LinearIndex` с полями:
- `embedding: number[]` (384-мерный вектор)
- `chatId`, `type`, `timestamp`
- Для exchange: `user`, `assistant`, `combined`, `chunkIndex`, `totalChunks`
- Для file: `fileName`, `content`, `chunkIndex`

### Псевдокод

```
addExchange(chatId, user, assistant):
  combined := "Q: " + user + "\nA: " + assistant
  chunks := chunkText(combined)
  Для каждого chunk:
     emb := embeddingService.embed(chunk)
     item := Exchange{ type: 'exchange', chatId, ..., embedding: emb }
     index.add(item, emb)
  saveIndex()

addFileChunk(chatId, fileName, chunkIndex, content):
  emb := embeddingService.embed(content)
  item := FileChunk{ ..., embedding: emb }
  index.add(item, emb)
  // Сохранение — отдельно через flushIndex.
```

### Граничные случаи

- **Embedding service не загружен.** Логируется предупреждение один раз,
  запись пропускается.
- **Batch загрузка.** `addFileChunk` не сохраняет индекс — вызывающий
  вызывает `flushIndex` после всего батча.
- **Длинный файл.** Каждый чанк эмбеддится и добавляется отдельно.

### Почему именно так

**Почему локальная модель (Xenova).** Нет внешних зависимостей, нет
API-ключей, работает офлайн. Модель all-MiniLM-L6-v2 — компромисс между
качеством (384-мерные векторы) и скоростью на CPU.

**Почему JSON-файл, а не SQLite/FAISS.** Ожидаемый объём — тысячи
фрагментов на сессию. Linear scan по JSON-массиву работает за миллисекунды,
а внешние зависимости (FAISS) ломают переносимость проекта.

**Почему разделены `addFileChunk` и `flushIndex`.** Сохранение индекса —
это запись всего JSON-файла. Если вызвать после каждого чанка, получится
O(n²) по I/O. `flushIndex` вызывается один раз после батча.

### Реализация

- `src/rag/HistoryStore.ts` → `addExchange()`, `addFileChunk()`, `flushIndex()`
- `src/rag/RealEmbeddingService.ts`
- `src/rag/LinearIndex.ts`

## R3. Поиск с фильтром по chatId {#r3}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Найти релевантные фрагменты, исключив записи текущего чата (они уже
в контексте — дублировать их незачем).

### Входные данные

- `query: string`.
- `currentChatId: string | null`.
- `topK: number` (обычно 5).

### Выходные данные

`SearchResult[]` — отфильтрованные и ранжированные результаты.

### Псевдокод

```
search(query, currentChatId, topK):
  Если embedding service не загружен — вернуть [].
  queryVec := embed(query)
  candidates := index.search(queryVec, topK * 4)
  candidates := candidates.filter(r => r.item.chatId !== currentChatId)
  Если candidates пусто — вернуть [].
  // Передать в R4 для ранжирования.
  Вернуть rank(candidates, topK)
```

### Граничные случаи

- **Чат новый, chatId = null.** Фильтр отсечёт записи с `chatId = null`
  (если такие есть). В текущей архитектуре записей с `null` в индексе
  не возникает — см. R5.
- **Все результаты из текущего чата.** Возвращается пустой массив.

### Почему именно так

**Почему фильтр, а не отдельный индекс на чат.** Индекс append-only,
разделение на подындексы усложнило бы поиск и переключение чатов.
Один линейный скан по всему индексу с фильтром по chatId — проще и
быстрее на нашем масштабе.

**Почему `topK * 4` кандидатов.** Часть отсеется фильтром, часть —
переранжируется по recency (R4). Если сразу взять `topK`, можно
потерять свежие записи, которые чуть ниже по similarity.

### Реализация

- `src/rag/HistoryStore.ts` → `search()`
- `src/rag/LinearIndex.ts` → `search()`

## R4. Ранжирование (semantic + recency) {#r4}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 2 (заменил ранжирование по чистому cosine similarity)

### Назначение

Выбрать из индекса пять наиболее релевантных фрагментов, учитывая не
только семантическую близость, но и свежесть записи.

### Входные данные

- Кандидаты после фильтрации (R3).
- `RAG_RECENCY_FLOOR` из `.env` (по умолчанию 0.7).
- `totalItems` — размер индекса.

### Выходные данные

Отсортированный по убыванию `score` массив `SearchResult[]`.

### Псевдокод

```
W := RAG_RECENCY_FLOOR (0.7)
denom := max(1, totalItems - 1)

Для каждого кандидата r:
  recency := r.storeIndex / denom       // 0 (старый) … 1 (новый)
  factor  := W + (1 - W) * recency       // W … 1
  score   := r.similarity * factor

Отсортировать по score убыванию.
Вернуть первые topK.
```

### Граничные случаи

- **Индекс из одного элемента.** `denom = 1`, `recency = 1`.
- **Все элементы одинакового возраста.** Recency влияет равномерно,
  порядок определяется similarity.
- **Очень старый, но очень релевантный.** Score = similarity * 0.7 —
  всё ещё может выиграть у свежего, но нерелевантного.

### Почему именно так

**Почему не чистая семантика.** Один и тот же вопрос со временем
получает разные ответы. Свежий ответ актуальнее старого с той же
формулировкой. Чистый cosine similarity этого не учитывает.

**Почему score — произведение, а не сумма.** Первая версия складывала
`α * similarity + (1 - α) * recency`. Это работало плохо: similarity
обычно в диапазоне 0.1–0.5, а recency в 0–1. Свежий, но нерелевантный
фрагмент выигрывал у старого, но релевантного. Произведение делает
recency множителем — семантика остаётся основным сигналом, свежесть —
модификатором в диапазоне [W, 1].

**Почему `topK * 4` кандидатов до фильтра.** Свежий фрагмент может быть
чуть ниже границы topK по similarity, но выиграть после умножения на
recency. Если бы сразу брали topK, он бы не попал в выборку.

**Почему позиция в индексе, а не timestamp.** Индекс append-only,
позиция монотонна по времени добавления. `Date.now()` даёт тот же
порядок, но недетерминирован между тестовыми прогонами.

### Реализация

- `src/rag/HistoryStore.ts` → `search()`
- `src/rag/LinearIndex.ts` → поле `storeIndex`
- `src/rag/types.ts` → `SearchResult`

## R5. Механизм переприсвоения chatId (reserved) {#r5}
**Статус:** reserved (не вызывается в текущей версии)
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Проставить реальный `chatId` записям, у которых он `null` — на случай,
если файл был проиндексирован до того, как DeepSeek присвоил чату ID.

### Текущее состояние

**Функция определена, но не вызывается.** В текущей архитектуре такая
ситуация невозможна: enqueue файлов в `IndexingQueue` гейтится на
`client.currentChatId`, который уже установлен в конце
`SendUserMessageTask.execute()`. Файлы всегда индексируются с реальным
`chatId`, и записей с `chatId = null` в индексе не возникает.

Механизм сохранён как страховка: если гейт в `chat.js` (шаг 8) когда-нибудь
изменится и файлы начнут попадать в очередь без `chatId`,
`reassignNullChatId` позволит исправить индекс без переиндексации.

### Входные данные

- `newChatId: string` — реальный ID чата, полученный после первого ответа.

### Выходные данные

Количество обновлённых записей; при `changed > 0` индекс сохраняется.

### Псевдокод

```
reassignNullChatId(newChatId):
  changed := index.reassignChatId(null, newChatId)
  Если changed > 0: saveIndex()
  Вернуть changed
```

### Почему не вызывается

**Почему не «подождать id и только потом индексировать».** Индексация
в фоне — оптимизация, не критичный путь. Ожидание ID до enqueue
не даёт выигрыша: `SendUserMessageTask` и так завершается до
возврата в `chat.js`. Проще проверить `client.currentChatId` в момент
enqueue (гейт) и пропустить операцию, если ID ещё нет, чем
переприсваивать постфактум.

**Почему механизм сохранён.** Удаление потеряло бы возможность
исправить индекс при изменении архитектуры enqueue. Определение
функции дешевле, чем восстановление логики через полгода.

### Реализация

- `src/rag/HistoryStore.ts` → `reassignNullChatId()`
- `src/rag/LinearIndex.ts` → `reassignChatId()`

### История

- v1 (2026-09-18): введён как страховка. В текущей версии не вызывается.

## R6. Фоновая индексация файлов {#r6}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Перенести эмбеддинг файлов из request-response цикла в фоновую очередь,
чтобы клиент не ждал минуты на больших файлах.

### Входные данные

- `filePath`, `apiKey`, `chatId`, `fileName`.

### Выходные данные

Проиндексированные фрагменты в `HistoryStore` сессии.

### Псевдокод

```
IndexingQueue.enqueue(job):
  Если shutdown — удалить файл, выйти.
  queue.push(job)
  process()

process():
  Пока queue не пусто и не shutdown:
     job := queue.shift()
     try:
        runJob(job)
     finally:
        deleteFile(job.filePath)

runJob(job):
  Если fileName начинается с "snapshot" или "rag_context_" — пропустить.
  Если !isIndexableFile — пропустить.
  content := readTextFileSafe(filePath)
  Если !content — пропустить.
  store := getHistoryStore(apiKey)
  chunks := chunkText(content, RAG_CHUNK_SIZE)
  Для каждого chunk: store.addFileChunk(chatId, fileName, i, chunk)
  store.flushIndex()
```

### Граничные случаи

- **Shutdown во время работы.** Текущий job дожидается, остальные
  удаляются с файлами.
- **Ошибка чтения файла.** Логируется, файл удаляется.
- **Service-файл (snapshot, rag_context).** Пропускается без индексации.

### Почему именно так

**Почему фоновая очередь, а не инлайн.** Файл 10 МБ = ~5000 чанков =
несколько минут CPU. Клиент не может ждать так долго — undici
таймаутит запрос через 5 минут. Очередь возвращает ответ сразу после
ответа DeepSeek, индексация происходит «потом».

**Почему один worker.** Embedding-модель — общий ресурс с ограниченным
параллелизмом. Два параллельных эмбеддинга конкурируют за CPU и не
ускоряют процесс (модель всё равно одна). Один worker достаточен.

**Почему service-файлы пропускаются.** `snapshot.txt` — это сводка,
не новые данные. `rag_context_*.txt` — фрагменты, извлечённые из
самого индекса. Их индексация создаёт feedback loop: индекс пухнет
копиями себя.

**Почему файл удаляется в `finally`.** Очередь владеет файлом с момента
`enqueue`. Что бы ни случилось (успех/ошибка/пропуск) — файл удаляется.

### Реализация

- `src/rag/IndexingQueue.ts`
- `server-modules/routes/chat.js` → enqueue после ответа (шаг 8)

## R7. Очистка индекса при fresh start {#r7}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Удалить все эмбеддинги текущей сессии, когда пользователь явно
запрашивает новый чат (`restore: false` или первый запуск).

### Входные данные

- `sessionId` (обычно apiKey).
- `ENABLE_RAG`.

### Выходные данные

Индекс пуст (файл `rag_data/<sessionId>.linear.json` truncate или
удалён через `store.clear()`).

### Псевдокод

```
clearHistoryStoreIfExists(sessionId):
  Если сессия есть в memory stores:
     store.clear() (fire-and-forget)
     Вернуть true

  filePath := rag_data/<sessionId>.linear.json
  Если файл существует:
     Записать '{"items":[],"vectors":[]}'
     Вернуть true

  Вернуть false
```

### Граничные случаи

- **Хранилище ещё не загружено (старт сервера).** Файл truncate без
  загрузки embedding-модели — быстро.
- **Хранилище в памяти (runtime).** Вызывается `store.clear()`,
  который перезаписывает файл пустым индексом.
- **RAG выключен.** `clearRagIndexIfEnabled` сразу выходит.

### Почему именно так

**Почему два пути (memory vs file).** Загрузка embedding-модели занимает
2–3 секунды. На старте сервера это недопустимо — поэтому файл truncate
напрямую. В runtime модель уже загружена, используется `store.clear()`.

**Почему fire-and-forget в memory-пути.** `clear()` возвращает Promise,
но никто не ждёт его завершения. Persistence пустого индекса не влияет
на логику — если сервер упадёт до записи, файл останется старым, но
при следующей загрузке `loadIndex` прочитает его и всё равно заполнит
пустым (потому что вызов уже был).

**Почему не удаление файла.** Truncate оставляет файл валидным JSON.
Удаление — если load упадёт до save, создаст ситуацию «файла нет»,
что обрабатывается, но менее предсказуемо.

### Реализация

- `src/rag/init.ts` → `clearHistoryStoreIfExists()`
- `src/DeepSeekClient.ts` → `clearRagIndexIfEnabled()`

## R8. Инъекция RAG-контекста в запрос как файла {#r8}
**Статус:** active
**Дата фиксации:** 2026-09-18
**Версия:** 1

### Назначение

Передать модели найденные фрагменты как **вложение**, а не как текст
промпта, чтобы модель относилась к ним как к доверенному источнику.

### Входные данные

- Результаты поиска `SearchResult[]`.
- `prompts/rag_upload_prompt.txt` — сопроводительная инструкция.

### Выходные данные

Временный файл `uploads/rag_context_<ts>.txt`, прикреплённый к текущему
сообщению; System-сообщение с инструкцией в промпте.

### Псевдокод

```
1. Сгруппировать результаты:
   - exchange — по (user, assistant), отсортировать по chunkIndex.
   - file — по одному блоку на чанк.

2. Собрать текст:
   [RAG context — retrieved from indexed history]
   --- Fragment (from earlier exchange) ---
   ...
   --- Fragment (from file: name) ---
   ...
   [End of retrieved context]

3. Записать файл uploads/rag_context_<ts>.txt.

4. Добавить путь в tempFilePaths (прикрепится к сообщению).

5. fullMessages.unshift({ role: 'system', content: uploadInstruction })
   prompt := buildPrompt(fullMessages, tools)

6. Enqueue файлов (всех, не только RAG-файла) в IndexingQueue —
   выполняется на шаге 8 chat.js, после возврата из SendUserMessageTask.
```

### Граничные случаи

- **Результатов нет.** Ничего не инъектируется.
- **Ошибка поиска.** Логируется, запрос выполняется без RAG-контекста.
- **Пустой фрагмент.** Пропускается.

### Почему именно так

**Почему файл, а не текст промпта.** Модель относится к тексту в промпте
как к потенциальной инъекции. Файл через UI — реальное вложение, модель
доверяет ему. Это стало очевидно после серии экспериментов: вставка
содержимого в `userText` приводила к ответам «файла нет в беседе».

**Почему System-инструкция префиксом.** `buildPrompt` добавляет префиксы
ролей, если есть System-сообщение или несколько сообщений. System
семантически правильнее — инструкция о доверии к файлу адресована
модели, а не пользователю.

**Почему `rag_context_` в имени файла.** `IndexingQueue.runJob` пропускает
эти файлы по префиксу. Без этого фрагменты индексировались бы повторно,
создавая feedback loop.

### Реализация

- `server-modules/routes/chat.js`
- `prompts/rag_upload_prompt.txt`
